# حاکمیت مهندسی پروژه

این قواعد هنگام بررسی مخزن، تصمیم فنی، نمونه اجرایی یا هر تغییر کد اعمال شوند. در فاز اول، کدنویسی تولیدی به‌طور پیش‌فرض خارج از محدوده است.

## معماری و مرجعیت منطق

- مرزهای دامنه را حول هویت و دسترسی، باشگاه، زمین، تقویم، رزرو، پرداخت، تسویه، بازیکن، مربی و مسابقه جدا نگه دار.
- رابط React/TypeScript فقط نمایش، تعامل و فراخوانی API را انجام دهد. دسترسی مستقیم به پایگاه داده یا فایل‌سیستم ممنوع است.
- FastAPI/Python یا سرویس بک‌اند منتخب، مرجع قواعد ظرفیت، قیمت، تخفیف، لغو، بازپرداخت، کارمزد، تسویه، سطح دسترسی و انتقال وضعیت باشد.
- منطق API در Service و Adapter، Routeها در Router مستقل و State فرانت‌اند در Hook/Store مشخص قرار گیرد.
- هیچ تابع یا فایل چند مسئولیت نامرتبط نداشته باشد. کامپوننت React بیش از ۳۰۰ خط باید پیش از رشد بیشتر تفکیک شود.

## خط مبنای فناوری

ترجیح فعلی `React + TypeScript` برای رابط، `FastAPI + Python` برای بک‌اند و `PostgreSQL` برای داده تراکنشی است. این ترجیح تصمیم قطعی نیست؛ فاز دوم باید آن را در ADR با گزینه‌ها، محدودیت‌ها و پیامدها تأیید یا جایگزین کند. فناوری را بی‌صدا تغییر نده.

## تغییر ایمن

1. پیش از تغییر، اثر آن را بر مدل‌ها، APIها، سرویس‌ها، رابط‌ها، تست‌ها، داده و سازگاری عقب‌رو فهرست کن.
2. برای تغییر مادی، تأیید کاربر را پس از تحلیل اثر بگیر.
3. فقط ناحیه هدف را تغییر بده؛ بازنویسی فایل سالم یا تغییر نام Props، Callback، Endpoint و Contract بدون ضرورت و تأیید ممنوع است.
4. هیچ کد ناقص، Stub نمایشی، تابع بی‌بدنه یا عبارت‌هایی مانند `existing code` تحویل نده.
5. خطا را در مرز مناسب مدیریت کن و پیام عملی و قابل‌فهم به کاربر نشان بده؛ خطای بی‌صدا در Console کافی نیست.

## تست و کیفیت

- قابلیت جدید با چرخه Red–Green–Refactor و تست جدید آغاز شود.
- تست موجود را برای سبزکردن پیاده‌سازی تغییر نده. اگر قرارداد واقعاً تغییر کرده است، مهاجرت تست را جداگانه توضیح بده و فقط با تأیید صریح انجام بده.
- پس از تغییر فرانت‌اند، Build و تست‌های مرتبط؛ پس از تغییر بک‌اند، `pytest` و کنترل Migration اجرا شود.
- پیش از تحویل، `git diff` و `git status` را برای تغییر ناخواسته، فایل تست دستکاری‌شده، Secret و Artifact اضافی بررسی کن.
- معیار پذیرش محصول باید به تست واحد، یکپارچه یا سرتاسری قابل نگاشت باشد.

## کارایی رابط

- `backdrop-blur` و `backdrop-filter: blur()` در مدال‌ها و لایه‌های پرتکرار ممنوع است.
- `transition-all` روی جدول، سطر و سلول استفاده نشود.
- جدول‌های عملیاتی از چیدمان ثابت، عرض ستون روشن و در صورت نیاز Virtualization استفاده کنند.
- رندرهای پرتکرار با Memoization، Callback پایدار و State محلی ایزوله شوند؛ ورودی‌های محاسباتی Debounce شوند.
- خاموش‌کردن شتاب‌دهنده سخت‌افزاری راه‌حل مشکلات UI نیست.
- هدف کارایی باید با اندازه‌گیری روی سخت‌افزار اداری ضعیف‌تر تأیید شود؛ ادعای ۶۰ فریم بدون پروفایل معتبر نیست.

## امنیت و داده

- Secret، Token، رمز و اطلاعات پرداخت در کد، لاگ یا نمونه داده ثبت نشود.
- داده سلامت، تصویر، موقعیت، پرداخت و اطلاعات شاگرد حداقل‌سازی و با دسترسی مبتنی بر نقش محافظت شود.
- عملیات مالی و رزرو حساس Idempotent و دارای Audit Trail باشد.
- Migrationها برگشت‌پذیر یا دارای برنامه بازیابی باشند و روی داده تولیدی بدون نسخه پشتیبان اجرا نشوند.

## ثبت تغییر

- تغییرهای پیاده‌سازی اتمیک و پس از عبور از تست‌ها با پیام فارسی روشن مانند `ویژگی: ...`، `اصلاح: ...`، `بهبود: ...` یا `مستندات: ...` ثبت شوند.
- در مخزنی که کاربر اجازه Push داده است، فقط همان تغییر تأییدشده و تست‌شده ارسال شود. شاخه محافظت‌شده یا جریان انتشار را دور نزن.
