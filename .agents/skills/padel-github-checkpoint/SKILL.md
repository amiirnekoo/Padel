# پروتکل ثبت Checkpointهای پروژه Padel در GitHub

این مهارت برای ثبت اتمیک، ایمن و مداوم تغییرات و تصمیم‌های معنادار پروژه در مخزن اختصاصی GitHub به نام `Padel` استفاده می‌شود.

## ۱. تعریف اقدام مهم

یک Checkpoint فقط پس از انجام یک «اقدام مهم» ثبت می‌شود.

### موارد مهم (شامل Checkpoint):
- تأیید یا تغییر یک تصمیم محصولی.
- ایجاد یا اصلاح سند مرجع پروژه (مانند اسناد `docs/product-state.md` و اسناد پوشه `docs/phase-01/`).
- تکمیل یک گیت (Gate)، فاز یا تحویل‌شدنی (Deliverable).
- تغییر دامنه، جریان کاربر (User Flow)، قواعد دامنه یا معیارهای پذیرش.
- تصمیم معماری، ساختار ماژول‌ها یا تدوین ADR.
- تکمیل یک قابلیت، زیرسیستم یا رفع باگ (Bug Fix).
- تغییر مدل داده، قراردادهای API یا تغییرات ساختاری.
- تغییر امنیتی، مالی، سازوکار رزرو، پرداخت، لغو یا تسویه.
- تکمیل مجموعه‌ای منسجم و تست‌شده از تغییرات.

### موارد غیرمهم (بدون ایجاد Checkpoint):
- صرفاً خواندن، فهرست کردن یا بررسی فایل‌ها.
- جست‌وجو و تحقیق بدون نتیجه نهایی و ثبت‌شده.
- گفت‌وگوی جاری با کاربر پیش از رسیدن به تصمیم یا خروجی.
- تغییرات موقت، فایل‌های چرک‌نویس یا کارهای نیمه‌کاره.
- فایل‌های لاگ، کَش یا خروجی‌های ساخت (Build outputs).
- ویرایش‌های صرفاً جزئی تایپی، مگر آنکه معنای تصمیم یا قراردادی را تغییر دهد.

## ۲. فرایند گام‌به‌گام ثبت Checkpoint

1. **بررسی تغییرات:** اجرای `git status` و `git diff` برای مشاهده دقیق وضعیت تغییرات.
2. **جداسازی دامنه تغییر:** تفکیک تغییرات مرتبط با اقدام جاری از فایل‌های چرک‌نویس، کارهای نیمه‌کاره یا تغییرات متفرقه کاربر.
3. **Stage اختصاصی:** صرفاً فایل‌های دقیقاً مرتبط با اقدام مهم را Stage کن (`git add <file>`). هرگز از `git add .` کورکورانه استفاده نکن.
4. **اعتبارسنجی و تست:** اجرای تست‌ها و اسکریپت‌های ارزیابی (مانند `python .agents/skills/define-padel-tennis-mvp/scripts/validate_phase1_docs.py .`).
   - در صورت عدم عبور از آزمون یا بروز خطا، عملیات Commit و Push را بلافاصله متوقف و مشکل را گزارش کن.
5. **بررسی امنیت و داده‌های حساس:** اطمینان از عدم وجود Secretها، کلیدها، توکن‌ها و فایل‌های `.env`.
6. **ایجاد Commit اتمیک:** ایجاد یک Commit تمیز، مشخص و با پیام استاندارد.
7. **ارسال به مخزن (Push):** ارسال تغییرات به Branch جاری روی Remote مخزن `Padel`.
8. **کنترل موفقیت:** بررسی نتیجه Push و تأیید ثبت موفقیت‌آمیز در Remote.

## ۳. استاندارد پیام‌های Commit

پیام Commit باید شفاف، خلاصه و به زبان فارسی همراه با یکی از پیشوندهای زیر باشد:

- `مستندات:` (برای ایجاد یا بروزرسانی اسناد تحلیل، محصول یا راهنما)
- `تصمیم:` (برای ثبت تصمیم‌های کلیدی دامنه، کسب‌وکار یا گیت‌های پروژه)
- `معماری:` (برای تغییرات سطح‌بالا، ساختار پوشه‌ها و قراردادهای فنی)
- `ویژگی:` (برای پیاده‌سازی قابلیت‌های جدید مصوب)
- `اصلاح:` (برای رفع خطاها، تعارض‌ها و باگ‌ها)
- `بهبود:` (برای بهینه‌سازی عملکرد، پالایش اسناد یا ریفکتور)
- `آزمون:` (برای افزودن یا اصلاح تست‌ها و اعتبارسنج‌ها)
- `پیکربندی:` (برای تنظیمات Git، ابزارها و اسکریپت‌های محیطی)

*نمونه‌ها:*
- `مستندات: تدوین منشور محصول و مرزبندی فاز اول پدل`
- `تصمیم: تثبیت مدل برابری قیمت و پرداخت دنگی در تهران`
- `پیکربندی: افزودن سیستم Checkpoint گیت‌هاب پروژه پدل`

از پیام‌های گنگ و نامفهوم مانند `update`، `changes`، `fix` یا `new version` اکیداً خودداری شود.

## ۴. حفاظت از اسرار و داده‌های حساس

موارد زیر تحت هیچ شرایطی نباید وارد مخزن شوند:
- فایل‌های محیطی (`.env` و امثال آن)
- توکن‌ها، API Keyها و پسوردها
- کوکی‌ها، سشن‌ها و لاگ‌های حاوی اطلاعات هویتی
- فایل‌های باینری و موقت، دایرکتوری `node_modules`، `.venv` و کش‌های پایتون

## ۵. قواعد ایمنی و پایداری Git

- هیچ‌گاه از `git push --force` یا `git reset --hard` استفاده نکن.
- شاخه‌ها، ریموت‌ها یا تاریخچه Git را بدون اجازه صریح کاربر تغییر نده.
- در صورت بروز Conflict، کار را متوقف و تعارض را گزارش کن.
- اگر عملیات Push به دلیل عدم احراز هویت یا قطعی ارتباط با خطا مواجه شد، وضعیت را شفاف اعلام کن تا کاربر وضعیت حساب GitHub خود را بررسی کند.
